# Stochastic block v0 — accuracy and correlation-sensitivity results

Issue #22. Generated by `../tb/accuracy_and_correlation_sweep.py`. Golden-model
methodology (LFSR construction, tap-mirroring convention) is the one
established and cross-validated against real RTL in `Microarch_Lib`
(`docs/adr/0002`, `docs/adr/0006` there) — this experiment reuses it rather
than re-deriving LFSR behavior from scratch.

## What this does NOT cover

This is a behavioral/statistical characterization via a Python golden model,
not a re-run of the gate-level or cocotb RTL simulation. The LFSR
construction and bit-comparison convention were already extensively
cross-validated against the actual RTL (`galois_lfsr.sv`,
`binary_stochastic_converter.sv`) in `Microarch_Lib`'s own test suite before
this experiment reused them, so this is not blind trust in an unverified
model — but a direct RTL/cocotb cross-check of these specific accuracy
numbers has not been run in this repo. That would be reasonable follow-up
scope for v1, not required for v0's evidence-gathering goal.

## Headline finding: naive seed-based decorrelation does not reliably work

`binary_stochastic_converter` instances driven by the *same LFSR polynomial*
at different integer seeds are **not** automatically independent. What
matters is the **phase lag** between the two seeds on the LFSR's own state
cycle, not the numeric difference between the seed values.

Measured directly: for the WIDTH=8 polynomial used throughout this project,
`phase_lag(seed=1, seed=2) = 1` — seed 2 is one single LFSR step ahead of
seed 1, not a "different" random position at all. The same 1-step lag holds
at WIDTH=4 as well.

**This directly implicates the default seeds used in `Microarch_Lib`'s
`test_b_mult_s_integration` and `test_b_add_s_integration` integration
tests** (`INIT_SEED_A=1`, `INIT_SEED_B=2`, at `WIDTH=4`) — those tests
verified *structural* correctness (`binary_out` is an honest popcount of
whatever the multiplier/adder actually output) but never checked numerical
fidelity to the true product/sum, by deliberate scope (documented in those
tests' own docstrings as "a separate characterization exercise"). This
experiment is that exercise, and it shows the exact seeds those tests use
are a near-worst-case choice for actual stochastic multiplication accuracy.

## Strategies compared

All at WIDTH=8 (period 255), five ways of sourcing the two operand
bitstreams for an AND-multiply, `N` up to 2^16:

| Strategy | Description |
|---|---|
| `true_random_control` | Genuine iid Bernoulli sampling (Python `random`), not LFSR-derived at all. The theoretical best case — isolates pure sampling noise from any LFSR-structural effect. |
| `shared_identical_seed` | Both operands from the literal same LFSR state sequence (the original bug shape, `docs/adr/0015` in Microarch_Lib). |
| `adjacent_seed_1_2` | Seeds 1 and 2 — the actual default used in this session's RTL integration tests. Phase lag = 1. |
| `half_period_seed` | Seed chosen so the phase lag from seed 1 is ≈ period/2 (127 of 255). A candidate mitigation. |
| `different_polynomial` | Operand B driven by a genuinely different LFSR width (different `TAPS_LUT` entry), the same decorrelation approach `stochastic_adder.sv`'s select LFSR already uses relative to its operand encoders. |

## Results (N = 65536, four representative (p1, p2) pairs)

| Strategy | avg abs error vs true product | Notes |
|---|---|---|
| `true_random_control` | ~0.0016 | Sampling-noise floor. |
| `shared_identical_seed` | ~0.131 | Estimates land near `min(p1,p2)` instead of `p1×p2` — the exact ADR 0015 bug shape. |
| `adjacent_seed_1_2` | ~0.038 | **This session's actual RTL default.** Better than fully shared, still a real, persistent error — not sampling noise (see below). |
| `half_period_seed` | ~0.0052 | Close to the true-random floor. Generalized across all 4 tested (p1,p2) pairs, not just one. |
| `different_polynomial` | ~0.0077 | Comparable to half-period-lag; a genuinely structurally different LFSR, not just a phase offset of the same one. |

Full per-pair, per-N data: `accuracy_vs_n.csv`, `correlation_sensitivity.csv`.

## Does the error shrink with N, or is it a fixed bias?

Directly checked for `(p1, p2) = (0.3, 0.7)`:

- `true_random_control`: error is noisy but trends down with N (0.0225 at
  N=16 → 0.0018 at N=65536) — classic sampling-noise convergence.
- `adjacent_seed_1_2`: error drops *only until N passes the LFSR's own
  period* (256), then **plateaus permanently** at ≈0.084 regardless of how
  much further N grows (0.0869 at N=512 vs 0.0841 at N=65536, barely
  moving). This is the direct proof that correlation error is a **fixed
  structural bias**, not something more samples can average away — a
  qualitatively different failure mode from ordinary stochastic-computing
  imprecision.

## Implication for the baseline arm

Two real mitigations were found and both generalize across the tested
(p1,p2) pairs: a carefully phase-separated seed on the same LFSR, or a
genuinely different LFSR polynomial per operand. Neither is what
`Microarch_Lib`'s current `DistinctEncoderSeeds`/
`SelectLFSRDecorrelatedFromOperands` elaboration checks (ADR 0015/0018)
actually enforce — those only reject the *identical* case, not the
near-identical-phase case that turned out to be the actual default. This is
exactly the "correlation-management cost" question your wiki roadmap
(`~/wiki/fpga_stochastic_blocks/index.md`, Active Architecture Questions)
already flagged as open, now with a first concrete answer: it's a real,
non-negligible design constraint for the LFSR-SC baseline arm, not a
solved problem, and it needs an explicit phase/polynomial-separation
strategy — not "pick any two non-equal seeds" — before this arm's accuracy
numbers can be trusted for the four-arm comparison.

## Fault tolerance (issue #33, A2)

`tb/fault_tolerance_sweep.py` -> `fault_tolerance.csv`. WIDTH=8 AND-multiply
(seeds 1 and 204, N=256) vs unprotected / parity / TMR 8x8 binary. Error is mean
|out - a*b/256| in % of full scale over 4000 random (a, b). Flip probability p is
per stored/transmitted bit per operation, uniform and 8-bit-burst models.

Mean error, uniform flips:

| p | SC stream | SC input reg | SC LFSR state | binary | binary + parity | binary TMR |
|---|---|---|---|---|---|---|
| 0 | 0.41 | 0.41 | 0.41 | 0.00 | 0.00 | 0.00 |
| 0.01 | 1.04 | 1.27 | 0.50 | 1.90 | 1.02 | 0.22 |
| 0.05 | 4.60 | 4.68 | 0.79 | 8.20 | 7.97 | 4.20 |
| 0.10 | 8.81 | 8.25 | 1.07 | 14.40 | 14.68 | 9.79 |
| 0.15 | 12.50 | 11.16 | 1.25 | 18.99 | 19.71 | 14.65 |

Reading: SC beats unprotected binary at every p >= 1% on the mean, and beats TMR
binary only at p >= 10% (about 10-15% lower). TMR wins clearly at p <= 2%. SC's
advantage is the tail: p99 error at p = 0.10 is 19.9 %FS for stream flips vs 55.9
(binary) and 55.9 (TMR). Flips in the 8-bit input registers are binary-style and
give SC a binary-sized tail (p99 23-58 %FS), so those registers need protection.
Parity as modelled (detect + one recompute) is a weak baseline. The SC LFSR-state
column is low only because that location has just 16 bits of exposure per op.

Caveats: the per-bit convention exposes SC to 768 stream bits against 32 binary
bits per op, but binary is only exposed for one cycle and SC for 256, so a
per-cycle rate would shift the comparison. Rates of 1-15% are far above real
soft-error rates; this shows scaling, not a field-failure claim. Area: SC multiply
is about 1.7x the DSP supertile, TMR is about 3x.
